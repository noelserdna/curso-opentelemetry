OpenTelemetry práctico

Instrumenta una mini tienda con Node.js y TypeScript. Verás sus trazas, métricas y logs primero en la terminal, después en Jaeger y en Grafana, y al final detrás de tu propio Collector.

  • 2sesiones de 105 minutos
  • 8módulos con reto y solución
  • 3señales: trazas, métricas y logs

La idea central

Tu app envía siempre la telemetría al mismo sitio: http://localhost:4318, con el protocolo OTLP. A lo largo del curso cambia quién escucha en ese puerto. El código de la app no cambia.

EtapaComandoDónde mirar
Sesión 1, M2 a M4npm run infra:jaegerlocalhost:16686
Sesión 2, M5 y M6npm run infra:lgtmlocalhost:3000
Sesión 2, M7 y M8npm run infra:collectorLas dos anteriores
Parar todonpm run infra:down

Cada comando infra:… para primero lo que hubiera arrancado, porque todas las etapas usan los mismos puertos. Los datos se guardan en memoria: al cambiar de etapa se empieza de cero.

Fundamentos y trazas

M0

Qué es OpenTelemetry

15 minSin código

El problema

Un cliente dice que pagar en tu tienda tarda tres segundos. La petición pasa por la API, el servicio de cupones, el de inventario y el banco. Cada uno escribe sus propios logs, en su propio formato. ¿Cuál de ellos se queda con los tres segundos?

Sin una forma común de seguir la petición de principio a fin, la respuesta es abrir cuatro ficheros de log y cruzar marcas de tiempo a mano.

Qué es y qué no es

OpenTelemetry es un estándar abierto, mantenido por la CNCF, para generar y enviar telemetría. Define una API, unos SDK para cada lenguaje y un protocolo de transporte.

OpenTelemetry no almacena ni dibuja nada. Entrega los datos a la herramienta que tú elijas. Por eso puedes cambiar de herramienta sin volver a instrumentar tu código.

Las tres señales

SeñalQué esPregunta que responde
TrazaEl recorrido de una petición, paso a paso¿Dónde se fue el tiempo de esta petición?
MétricaUn número que se agrega en el tiempo¿Cuántos pedidos por minuto? ¿Va a peor?
LogUn mensaje escrito en un instante¿Qué ocurrió exactamente en ese momento?

Vocabulario de una traza

Span
Una operación con nombre, inicio y fin: «cobrar», «GET /productos».
Traza
Todos los spans de una misma petición, enlazados como un árbol de padres e hijos.
Atributo
Un dato del span para buscar y filtrar: cupon.codigo = "VERANO5".
Evento
Un momento concreto dentro de un span: «pago autorizado».
Estado
Si la operación terminó bien o con error.
Recurso
Quién emite la telemetría: nombre y versión del servicio, máquina, proceso.
M1

Tu primer span

10 minTerminalTrazas

Objetivo

Crear una traza de tres spans y leerla en la terminal. Sin servidor y sin Docker.

Pasos

npm run m1

Abre modulos/m1-primer-span/main.ts. Todo el módulo cabe en tres ideas:

// 1. El SDK decide qué hacer con los spans: aquí, imprimirlos.
const sdk = new NodeSDK({
  serviceName: 'tienda',
  spanProcessors: [new SimpleSpanProcessor({ exporter: new ConsoleSpanExporter() })],
});
sdk.start();

// 2. El tracer es la fábrica de spans de tu código.
const tracer = trace.getTracer('curso.m1');

// 3. Un span se abre, hace su trabajo y se cierra.
await tracer.startActiveSpan('preparar-pedido', async (span) => {
  span.setAttribute('pedido.id', 1001);
  await validarStock();   // abre su propio span, hijo de este
  await calcularTotal();
  span.end();
});

Qué debes ver

Tres bloques, uno por span. Este es el primero, resumido:

{
  resource: { attributes: { 'service.name': 'tienda', … } },
  instrumentationScope: { name: 'curso.m1' },
  traceId: '0c7620e0eca8295153d8016609d9d96d',
  parentSpanContext: { spanId: '342ab18348119b0f', … },
  name: 'validar-stock',
  id: '48df9a25dfa9273d',
  duration: 40374.334,
  attributes: { 'stock.disponible': true },
}
CampoQué significa
traceIdIdentifica la traza. Es el mismo en los tres spans.
idIdentifica este span.
parentSpanContext.spanIdEl id de su padre. En preparar-pedido no existe: es la raíz.
durationDuración en microsegundos: 40374 son unos 40 ms.

Los hijos aparecen antes que el padre. Un span se exporta cuando termina, y el padre termina el último.

Reto

Añade al span padre el atributo pedido.items y crea un tercer span hijo llamado enviar-confirmacion.

Ver la solución 
npm run m1:solucion

El código está en modulos/m1-primer-span/solucion.ts. Ahora salen cuatro spans con el mismo traceId.

M2

Auto-instrumentación

25 minTerminal, después JaegerTrazas

Objetivo

Obtener trazas de una API Express sin escribir código de OpenTelemetry en ella, y verlas en Jaeger.

Paso 1. Sin tocar nada: solo variables de entorno

npm run m2:zero

En la otra terminal:

npm run probar m2

La terminal de la app se llena de spans. Ahora abre modulos/m2-auto/app.ts: no hay ni una línea de OpenTelemetry. Toda la configuración está en env/zero-code.env:

OTEL_SERVICE_NAME=tienda
OTEL_TRACES_EXPORTER=console
OTEL_METRICS_EXPORTER=none
OTEL_LOGS_EXPORTER=none
OTEL_NODE_ENABLED_INSTRUMENTATIONS=http,express

Paso 2. La misma configuración, en código

Para la app con Ctrl + C y arranca esta variante:

npm run m2:consola

El resultado es el mismo, pero ahora la configuración vive en modulos/m2-auto/instrumentation.ts. La clave está en cómo se arranca:

tsx --import ./modulos/m2-auto/instrumentation.ts modulos/m2-auto/app.ts

--import carga la instrumentación antes que la app. Cuando la app hace import express, la librería ya está preparada para crear spans.

Paso 3. De la terminal a Jaeger

npm run infra:jaeger

Para la app y arráncala en su modo normal, que envía por OTLP:

npm run m2
npm run probar m2

Abre http://localhost:16686, elige el servicio tienda y pulsa Find Traces.

Qué debes ver

Cuatro trazas, una por petición. Cada una tiene tres spans, uno dentro de otro:

El span se llama GET /productos/:id y no GET /productos/1. Usa la ruta, no la URL: así todas las peticiones a esa ruta se agrupan bajo un mismo nombre.

Reto

Una de las cuatro peticiones devolvió un 404. Encuéntrala en Jaeger sin abrir las trazas una a una.

Ver la solución

En el buscador de Jaeger, escribe esto en el campo de etiquetas (Tags) y vuelve a buscar:

http.response.status_code=404

Cada atributo de un span es un criterio de búsqueda. Por eso merece la pena elegirlos bien.

M3

Spans manuales

30 minJaegerTrazas

Objetivo

La auto-instrumentación ve la petición HTTP, pero no sabe nada de tu negocio. Vas a añadir spans propios a un checkout y a usarlos para encontrar una lentitud escondida.

Pasos

Con Jaeger arrancado (npm run infra:jaeger):

npm run m3
npm run probar m3
Qué debes ver
Caso                      Petición              HTTP   Tiempo
----------------------------------------------------------------
Sin cupón                 POST /checkout        201    111 ms
Cupón VERANO5             POST /checkout        201    114 ms
Cupón BIENVENIDA10        POST /checkout        201    913 ms
Importe alto              POST /checkout        402    91 ms
Producto que no existe    POST /checkout        404    2 ms

Tus tiempos variarán unos milisegundos. La diferencia entre cupones, no.

Con el cupón BIENVENIDA10 el checkout tarda casi un segundo. En Jaeger, busca las trazas de tienda y abre la más larga.

Pulsa el span aplicar-cupon y mira sus atributos: cupon.codigo = BIENVENIDA10 y cupon.comprobaciones = 40. Ese segundo dato es la pista.

El patrón de un span manual

Está en modulos/m3-spans-manuales/checkout.ts. Todos los spans del módulo siguen esta forma:

return tracer.startActiveSpan('validar-carrito', async (span) => {
  try {
    span.setAttribute('carrito.items', carrito.items.length);
    // … lógica de negocio …
  } catch (error) {
    span.recordException(error as Error);                  // guarda el error
    span.setStatus({ code: SpanStatusCode.ERROR });        // marca el span como fallido
    throw error;
  } finally {
    span.end();                                            // sin end(), el span no se exporta
  }
});

recordException no basta. Guarda el error como evento, pero el span sigue contando como correcto. Es setStatus el que lo marca en rojo. Compruébalo en la traza del caso «Importe alto»: el span cobrar tiene las dos cosas.

Reto

Explica por qué aplicar-cupon tarda 823 ms con BIENVENIDA10 y solo 21 ms con VERANO5. Después arréglalo en checkout.ts.

Pista: cupon.comprobaciones vale 40 en un caso y 1 en el otro.

Ver la solución

El código recorre la lista de cupones y consulta la base de datos una vez por cada uno hasta encontrar el que busca. VERANO5 es el primero de la lista y BIENVENIDA10 el último, de 40.

La solución usa un Map indexado por código: una sola consulta, esté donde esté el cupón.

npm run m3:solucion

Repite npm run probar m3: el caso de BIENVENIDA10 baja de 913 ms a 102 ms. El código está en checkout.solucion.ts.

Pasos

npm run m4:inventario

En la segunda, los pedidos:

npm run m4:pedidos

En la tercera, las peticiones:

npm run probar m4

Qué debes ver

En la terminal del inventario, la cabecera con la que llega cada petición:

GET /stock/1  traceparent: 00-0dfefaa1c8e3a084c7734a04ddf4d5a4-a7aa6112c301bafe-01

M5

Métricas

25 minGrafanaTrazasMétricas

Objetivo

Cambiar de Jaeger a Grafana sin tocar la app, y medir el negocio: cuántos pedidos se crean y de qué importe.

Pasos

npm run infra:lgtm

Grafana tarda alrededor de un minuto en arrancar. El comando espera hasta que está listo.

npm run m5
npm run trafico

Abre http://localhost:3000, entra en Explore y elige la fuente de datos.

Primero, las trazas de siempre

Fuente de datos Tempo, pestaña Search, servicio tienda. Son las mismas trazas que veías en Jaeger, en otra herramienta.

El buscador de Tempo tarda unos 30 segundos en mostrar las trazas recién enviadas. Jaeger las muestra en dos.

Después, las métricas

Están definidas en modulos/m5-metricas/metricas.ts:

const meter = metrics.getMeter('tienda');

// Counter: un número que solo sube. Responde a «¿cuántos?».
export const pedidosCreados = meter.createCounter('tienda.pedidos.creados');

// Histogram: reparte los valores en tramos. Responde a «¿cómo se distribuye?».
export const importePedido = meter.createHistogram('tienda.pedido.importe', { unit: 'EUR' });

Y se usan en app.ts cada vez que se crea un pedido:

pedidosCreados.add(1, { 'pago.metodo': metodoPago });
importePedido.record(total, { 'pago.metodo': metodoPago });

En Grafana, fuente de datos Prometheus, modo Code. Prueba estas consultas:

PreguntaConsulta
Pedidos por método de pagosum by (pago_metodo) (tienda_pedidos_creados_total)
Importe medio de un pedidosum(tienda_pedido_importe_EUR_sum) / sum(tienda_pedido_importe_EUR_count)
Peticiones por código HTTPsum by (http_response_status_code) (http_server_request_duration_seconds_count)
Latencia del 95 % de las peticioneshistogram_quantile(0.95, sum by (le) (rate(http_server_request_duration_seconds_bucket[5m])))

Las dos últimas no las has programado tú. Las métricas http_server_… las crea la auto-instrumentación.

Tres instrumentos, tres formas

El tipo de instrumento depende de cómo se comporta lo que mides. Estos son los tres del módulo, con los datos de 300 peticiones seguidas:

Los nombres cambian por el camino

En tu códigoEn PrometheusPor qué
tienda.pedidos.creadostienda_pedidos_creados_totalLos puntos pasan a guiones bajos y los contadores ganan _total
tienda.pedido.importetienda_pedido_importe_EUR_bucket, _sum, _countSe añade la unidad, y un histograma son tres series
pago.metodopago_metodoLos atributos pasan a ser etiquetas

Cuidado con los atributos de una métrica. Cada combinación de valores crea una serie nueva. pago.metodo tiene tres valores y es seguro. El identificador de un pedido o un email tendrían miles, y dispararían el coste.

Reto

Añade una métrica tienda.stock.disponible que indique cuántas unidades quedan de cada producto. Un contador no sirve, porque el stock sube y baja.

Ver la solución

Se usa un observable gauge. No lo actualizas tú: el SDK te pregunta el valor cada vez que exporta.

const stockDisponible = meter.createObservableGauge('tienda.stock.disponible');

stockDisponible.addCallback((resultado) => {
  for (const producto of productos) {
    resultado.observe(producto.stock, { 'producto.nombre': producto.nombre });
  }
});
npm run m5:solucion

Lanza tráfico y consulta tienda_stock_disponible en Grafana: baja a medida que entran pedidos.

M6

Logs

30 minGrafanaTrazasMétricasLogs

Objetivo

Unir los logs con las trazas. Partiendo de un log de error, llegar en un clic a la traza de esa misma petición.

Pasos

Con Grafana arrancado (npm run infra:lgtm):

npm run m6
npm run probar m6

Paso 1. El trace_id aparece solo

Mira la terminal de la app. El logger es un pino normal (modulos/m6-logs/logger.ts), pero cada log escrito durante una petición lleva tres campos nuevos:

{"level":30, "msg":"Pedido creado", "producto":"Teclado mecánico", "total":89.9,
 "trace_id":"e1bc4a6797909dcf007a7aecc1ed88ac", "span_id":"9753dc0a9d6f21d4", "trace_flags":"01"}

Los añade la instrumentación de pino. El log de arranque, «Tienda escuchando», no los lleva: no pertenece a ninguna petición.

Paso 2. Los logs también viajan por OTLP

El único cambio está en instrumentation.ts:

logRecordProcessors: [
  new BatchLogRecordProcessor({ exporter: new OTLPLogExporter() }),
],

En Grafana, fuente de datos Loki, modo Code:

Qué buscasConsulta
Todos los logs de la tienda{service_name="tienda"}
Solo los errores{service_name="tienda"} | detected_level="error"
Los que contienen un texto{service_name="tienda"} |= "Pago rechazado"

Paso 3. Del log a la traza

Despliega un log de error. Entre sus campos está trace_id, con un enlace a Tempo. Al pulsarlo se abre la traza de esa petición, con el span cobrar marcado como fallido.

El camino inverso también existe. Desde un span en Tempo, el enlace a los logs muestra solo los de esa traza.

Reto

Lanza npm run trafico y, usando solo Grafana, responde: ¿por qué se rechazan algunos pagos?, ¿con qué método de pago? y ¿de qué importe?

Ver la solución
  1. En Loki, busca {service_name="tienda"} | detected_level="error".
  2. Despliega un log «Pago rechazado». El campo exception_message dice: «Bizum no admite pagos de más de 500 €».
  3. Pulsa el enlace de trace_id. En la traza, el span cobrar tiene pago.metodo = bizum y pago.importe = 747.

El log dice qué pasó. La traza dice dónde y con qué datos.

M7

Collector

25 minCollector, Jaeger y GrafanaTrazasMétricasLogs

Objetivo

Poner un Collector propio entre la app y las herramientas, enviar a Jaeger y a Grafana a la vez, y eliminar un dato personal antes de que salga.

Pasos

npm run infra:collector
npm run m7
npm run trafico

Qué debes ver

Las mismas trazas en Jaeger y en Grafana. La app las envía una sola vez; el Collector las reparte. Para ver lo que pasa por él:

npm run collector:logs

Cómo se configura

Todo está en infra/otelcol.yaml. Un Collector es una tubería con tres tipos de piezas, conectadas en un pipeline por cada señal.

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: [otlp_grpc/jaeger, otlp_http/lgtm, debug]

El problema

En Jaeger, abre una traza y pulsa el span request handler - /pedidos. Entre sus atributos está usuario.email, con el correo del cliente. La app lo guarda a propósito, como ejemplo de mala práctica: un dato personal acaba de salir hacia dos herramientas.

Reto

Haz que el email no salga del Collector, sin tocar la app. En infra/otelcol.yaml hay un procesador attributes/privacidad comentado. Actívalo, añádelo al pipeline de trazas y reinicia:

npm run collector:reiniciar

Lanza tráfico de nuevo y comprueba las trazas nuevas en Jaeger.

Ver la solución 
processors:
  batch:
    timeout: 1s
  attributes/privacidad:
    actions:
      - key: usuario.email
        action: delete

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [attributes/privacidad, batch]   # antes de batch
      exporters: [otlp_grpc/jaeger, otlp_http/lgtm, debug]

También puedes arrancar el Collector con la solución ya aplicada:

npm run infra:collector:solucion

Las trazas anteriores al cambio conservan el email. Las nuevas ya no lo tienen.

M8

Sampling y buenas prácticas

20 minCollector, Jaeger y GrafanaTrazas

Objetivo

Guardar todas las trazas es caro y casi nunca hace falta. Vas a quedarte con una parte, primero a ciegas y después eligiendo las que importan.

Head sampling: decide la app

Con el Collector arrancado (npm run infra:collector), para la app y arráncala así:

npm run m8
npm run trafico -- 40

Es la misma app del módulo 7. El único cambio es env/sampling.env:

OTEL_TRACES_SAMPLER=parentbased_traceidratio
OTEL_TRACES_SAMPLER_ARG=0.25

Qué debes ver

En Jaeger, alrededor de 10 trazas de las 40 peticiones. El número varía en cada ejecución porque es una probabilidad: en la prueba del curso salieron 7.

SeñalQué ocurre con el sampling al 25 %
TrazasSe guarda 1 de cada 4. Las que se guardan llegan completas.
MétricasNo les afecta. Con 7 trazas guardadas, el contador marcó los 31 pedidos creados.
LogsSe guardan todos. Los de trazas descartadas llevan trace_flags: "00".

El inconveniente: la decisión se toma al empezar la petición, sin saber cómo va a acabar. La traza del único error del día puede ser una de las descartadas.

Tail sampling: decide el Collector

El Collector espera a que la traza termine y decide con ella delante. Esta configuración, en infra/otelcol.tail-sampling.yaml, conserva las trazas con error y las que tardan más de 200 ms:

tail_sampling:
  decision_wait: 5s
  policies:
    - name: con-errores
      type: status_code
      status_code: { status_codes: [ERROR] }
    - name: lentas
      type: latency
      latency: { threshold_ms: 200 }
npm run infra:collector:tail
npm run m7
npm run trafico -- 40

En Jaeger quedan solo los pagos rechazados y las transferencias, que tardan 300 ms. Los pedidos rápidos y correctos se descartan. Puede colarse la primera petición tras arrancar la app, que es lenta porque Node aún está calentando.

Las trazas tardan unos segundos más en aparecer: el Collector espera decision_wait antes de decidir.

Buenas prácticas para llevarte

  • Define siempre service.name. Sin él, tu servicio aparece como unknown_service.
  • Nombra los spans por la operación, no por el dato. GET /productos/:id, nunca GET /productos/42.
  • Usa las convenciones semánticas cuando existan (http.request.method) y un prefijo propio para tu negocio (pedido., cupon.).
  • Ningún dato personal ni secreto en atributos. Y un Collector que los elimine, por si se cuela alguno.
  • Atributos de métricas con pocos valores posibles. Nunca identificadores ni emails.
  • Cierra siempre el span en un finally, y marca los errores con recordException y setStatus.
  • Llama a sdk.shutdown() al parar el proceso, o perderás los últimos datos.
  • Fija las versiones de los paquetes de OpenTelemetry. Cambian a menudo.

Lo que este curso no cubre

Instrumentación en el navegador, despliegue en Kubernetes con el Operator, perfiles de rendimiento y otros lenguajes. Los conceptos son los mismos: spans, atributos, recursos, OTLP y Collector.
